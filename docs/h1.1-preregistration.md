# H1.1 pre-registration — cross-vendor skeptic

**Status:** owner-approved 2026-09-19 ("yes, commit it as well documented decision"); frozen on commit; in-place amendments permitted until the first verifier run, then `h1.1-preregistration-v2.md`.
**Owner:** alex (decisions). **Evaluator:** the assistant session's evaluator agents (as for H1). **Engine:** `engine-coder`. **Miner:** nothing new — the cohort is reused.
**Parent:** `h1-preregistration.md` (frozen at `af582f6`), results `engine-runner/docs/h1-results.md` (`96f7d50`).

## 1. What H1 established, and the gap

On the frozen 40-case cohort, both Opus reviewers catch essentially every real escape (T recall 1.000, G 0.933) but flag many clean changes (T 11/20, G 6/20). The pilot showed a same-model verification stage is inert (4/77 dispositions moved, 0/3 wrong rejections rescued). The untested lever is a verifier that does not share the reviewer's weights.

## 2. Hypothesis

A **different-vendor verifier** (OpenAI Codex, `codex exec`), given the reviewer's primary finding and the same review-time bundle, rejects enough false RISKY calls that precision rises materially, while nearly all true RISKY calls survive.

## 3. Pass / fail — fixed now

Applied to each Opus arm separately (T′ = T after verification, G′ = G after verification):

| Criterion | Threshold |
|---|---|
| Precision, T′ vs T | ≥ +15 points |
| Precision, G′ vs G | ≥ +15 points |
| Recall lost, per arm | ≤ 1 positive (recall′ ≥ recall − 1/positives) |

H1.1 **passes** if both precision criteria hold and neither arm loses more than one positive. A pass on one arm only is reported as partial, not a pass. Significance (paired exchangeable-verdict test, T′−T and G′−G) is reported, non-criterial — at 11 and 6 false positives the precision moves needed are 8 and 4 cases.

Reported, not criterial: INCONCLUSIVE rate; verifier reason match against the fixing diff (same judge, same rule as H1 §6/D20); per-class and per-stratum breakdowns from H1.

## 4. What is reused, unchanged

Cohort (records_sha256 `b2279b9c…`), labels, keys, fixing paths and patches, probe gate (probe void stands), H1's sealed T and G runs and their `verdict.json`, the §8 scan verdicts (scan-voided runs stay voided), the judge, the scorer. No arm is re-run.

## 5. The verifier stage

- Protocol `h1.1-v1`, one stage `verifier`, model Codex (exact model string recorded), tools Read/Grep/Glob on the frozen `reviewer/` bundle, no oracle material.
- Input: the case bundle plus the arm's **primary finding** (file, line, mechanism, evidence, recommended validation) — not the arm's full review, not the other arm's finding.
- Output `h1-verify/v1`: `disposition ∈ {CONFIRMED, REJECTED, INCONCLUSIVE}`, restated mechanism, evidence lines, reason. Prompt is a fresh generic "adversarial verifier" prompt with H1's calibration paragraph; no domain lenses; it contains no PR number, SHA, CVE or FRR-derived code.
- Verdict rule: RISKY′ = RISKY ∧ CONFIRMED. INCONCLUSIVE and REJECTED → CLEAN′. CLEAN cases are not verified and stay CLEAN.
- Runs: every unvoided RISKY (case, arm) pair from H1 — ~27 T + ~20 G.
- **Unparseable output rule (fixed now):** a verifier response that fails schema validation is **INCONCLUSIVE — no retry**. A retry would let the measured quantity (rejection) move on a second draw. Retries are therefore not used for the disposition; the count of unparseable first responses is recorded in every sealed row and reported beside every H1.1 figure. Cap kills follow H1 §9 (flagged `retried`, reported separately).
- Credential kind (`auth_mode`) and safety flags are sealed per run as in H1; the Codex binary version and image digest are in the fingerprint.

## 6. Contamination controls

- Codex is probed (Probe A/B, no tools) on the 19 positives before any verifier run; a hit voids the case for H1.1 (in addition to H1's probe void). Codex training cutoff recorded.
- The steering control (planted CLAUDE.md/AGENTS.md) is run once on the Codex adapter under the verifier grant before the stage starts.
- §8 post-hoc scan runs over every sealed verifier output with the same keys and rules (A7); any hit voids that (case, arm).

## 7. Budget and stopping

Estimate: verifier ≈ $100–150 (≈47 runs), probes ≈ $10, steering ≈ $5, judge on confirmed TPs ≈ $5. **Cap $300** including adapter shakedown. Stop early only for a harness defect.

## 8. What this does not claim

Nothing about generalisation beyond FRR or beyond this cohort; nothing about a Codex reviewer arm (it is a verifier here); nothing about product readiness. A pass says a second vendor removes false alarms on this cohort; the reason-match and per-class reads say whether it removed the right ones.

## 9. Roles and blinding

The engine builds the adapter and stage without seeing H1's per-case verdicts or scores; the evaluator runs probes, steering, the verifier batch, scan, judge and scorer; results go to the owner only. Nobody who implements the scoring change receives interim numbers (H1 D19).

## 10. Amendments (before the verifier batch completes)

**A1 (2026-09-19, owner decision on cost).** After 21 (case, arm) pairs were verified in subset order — 17 true positives (all CONFIRMED on the primary finding) and 4 false positives (all CONFIRMED) — the remaining verifications are restricted to the 12 not-yet-verified **false-positive** pairs. Consequences, stated: (i) the list is label-derived, so the engine side can infer which cases are negatives; the H1.1 scorer was frozen (engine 4fac362) before the list existed and no scoring change follows; (ii) the recall-loss criterion (§3) is scored on the 17 true-positive pairs already verified, not on the full set. Precision criteria are unaffected: T′ and G′ precision are computed over all RISKY pairs, with unverified true positives kept as CONFIRMED by assumption (i).

**Process note.** Eleven verifications (8 G pairs) ran before this document was committed; all scoring took place after. Recorded rather than hidden.
